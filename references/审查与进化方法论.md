# 审查与进化方法论

以证据驱动 AI Agent 技能的诊断、修改与验证。四阶段流程是组织方式，不是每次都要执行的固定工作量。

## 目录

- 一、五大架构形态判定与自适应考量
- 二、四阶段工作流与安全边界
- 三、SEI 评估矩阵与适用限制
- 四、完整报告与分层事实卡

## 一、五大架构形态判定与自适应考量

| 形态 | 典型特征 | 优先检查 | 验证方式 |
|---|---|---|---|
| PROMPT | 以 SKILL.md、references、evals 为主 | 触发边界、指令矛盾、输出格式、臆造事实 | 代表性输入与负向反例；不强塞空脚本 |
| CLI | scripts 中有确定性工具 | 参数、退出码、文件边界、跨平台与依赖 | 原有自测入口、坏输入、语法解析 |
| MCP | MCP 配置或工具协议桥接 | Tool Schema、凭据、协议错误、超时 | 隔离测试服务或已授权环境 |
| PIPELINE | stages/steps 或多阶段编排 | 状态转移、幂等、产物有效性、失败恢复 | 覆盖实际状态转换和中断恢复 |
| HYBRID | 脚本与评测、知识库或多阶段组合 | 接口一致性与跨文件依赖 | 按实际改动选择上述验证方式 |

脚本形态检测只使用目录与文本特征，不保证识别完整。以真实调用链修正人工判断，不为匹配分类而改目录。

## 二、四阶段工作流与安全边界

### 阶段 1：全方位现状诊断（只读体检）

1. 定位目标目录与回归入口，检查 Git 状态，保留用户已有改动。
2. 运行一次静态审计作为基线，结合源码确认影响。FAIL、WARN 与 INFO 规则定义以静态规则清单为准；未自动实现的检查不冒充已完成。
3. 按风险读取坑库相关条目。对确认的缺陷记录路径、位置、触发条件、实际结果与期望结果。
4. 动态运行是独立的执行授权边界：检查自测脚本及它调用的命令后，再决定环境是否适合执行。`--dynamic` 不是隔离机制，也不保证零写入或零网络。
5. 单纯体检在此交付结果，不创建计划工单、注入脚手架或修复文件。

#### 命令行为

| 命令 | 默认行为 | 显式写入 |
|---|---|---|
| `audit.py <目标>` | 静态扫描并输出控制台报告 | `--report-file <路径>` 保存完整 Markdown |
| `audit.py <目标> --json` | 标准输出只含 JSON | 可同时加 `--report-file`，保存提示走 stderr |
| `audit.py <目标> --report` | 输出完整 Markdown | 同上 |
| `audit.py <目标> --dynamic` | 运行目标 selftest；默认超时 600 秒 | 目标代码可能产生任意副作用；`--timeout` 可调整时限 |
| `evolve.py <目标> --analyze` / `--plan` | 输出分析或方案 | `--plan -o <路径>` 保存方案 |
| `evolve.py <目标> --research-plan` | 输出候选查询，不创建工单 | 加 `--write-task` 持久化任务 |
| `evolve.py <目标> --offline-fallback` | 创建离线启发式草稿及任务状态 | 命令本身就是写操作 |
| `evolve.py <目标> --scaffold-test` / `--scaffold-prompt` / `--scaffold-all` | 创建相应脚手架，已有文件默认保留 | `--force` 可覆盖，需另确认 |

`--stdout` 保留兼容，默认审计不再生成 `audit-report.txt`。审计输出格式 `--json`、`--markdown`、`--report` 互斥。退出码 0 表示已检查项无 FAIL，1 表示发现 FAIL，2 表示命令用法或输出错误；退出 0 不表示所有动态或人工检查已完成。

### 阶段 2：方案设计与按需检索

先选择有证据、可验证且收益明确的改动。小范围缺陷直接设计修复，不用外部研究阻塞本地工作。

需要外部知识时，`--research-plan` 提供四维共 12 组候选查询：

- 同类 Agent 技能：触发描述、流程组织、评测边界；
- 开源工程：接口设计、错误处理、维护中的实现；
- 官方规范：协议、版本兼容与标准语义；
- 生产故障：相关边缘条件、静默失败、跨平台差异。

查询按问题筛选，不预设查询次数、星数门槛或强制全文篇数。优先阅读直接相关的官方文档和源码；以维护状态、版本与可复现行为判断适用性。使用宿主已有工具，不假定固定工具名。

记录已读 URL、解决的问题、适用版本、可迁移结论和未确认部分。代码片段可先做 AST/语法验证，但语法通过不代表 API 或业务行为正确。

**离线处理**：说明无法核验的外部事实。确需草稿时显式运行 `--offline-fallback`；`OFFLINE_HEURISTIC_FALLBACK` 表示启发式来源，而不是联网研究完成。普通修复不依赖这个文件。

**任务状态**：`--research-plan --write-task` 用于持久化研究进度；同领域重跑保留已有状态和元数据。工单只是记录，不是自动执行搜索的证明，也不会自行阻止所有后续动作。

### 阶段 3：处方施工与结构治理

#### 1. 引用改写：补读取时机，不追求统一口号

弱表达：“可参考故障手册。”

可执行表达：“遇到超时错误时，读取故障手册中的超时章节，按返回码选择下一步。”

已有清楚时机的引用不反复改写；参数字典与长示例留在 references，入口保留路由。

#### 2. 真实依赖：检验产物内容，不只检验文件存在

如果后续阶段确实依赖某项输入，明确有效结构、版本和失败处理，并在实际消费点校验。空 JSON、状态标签或包含关键词都不足以证明工序完成。

负向夹具至少覆盖与本次缺陷对应的坏输入，例如缺字段、无效状态、崩溃退出或超时。先确认旧行为失败，再验证修复；不要仅测试独立正则而绕过真正的入口。

#### 3. 只读与治理解耦（Zero-Mutation）

诊断默认不写目标目录。报告导出、任务持久化和脚手架生成属于显式写操作；动态实跑属于代码执行，不应写成“只读体检”。

用户提出优化即授权范围内修改；提交、推送和发布分别遵循用户的实际授权。已有修改先保留，覆盖与删除列清单；不自动删掉既有报告或用户成果，不以提高 SEI 为理由重写无关内容。

#### 4. 大改安全边界

大范围重构先列兼容性影响和恢复办法，在临时副本或独立环境构造破坏夹具。使用已有测试，不重复搭建同类框架；脚手架只是示例起点，生成后补真实领域用例并接入已有入口。

### 阶段 4：按风险验证与交付

- 小改：改动路径的语法/配置检查、代表性正向用例和对应负向回归。
- 共享规则、接口或大改：一次相关全量回归；改变触发描述时覆盖触发用例家族。
- 静态差分：确认新增问题，解释已知误报或遗留 WARN，不为了绿标放宽真实缺陷门槛。
- 清理：仅处理自己生成、确认可丢弃的临时产物；保留用户文件与正式报告。
- 交付：列出修改、实际命令及结果、未验证范围与剩余风险。没有测量的耗时或 SEI 不编造前后对比。

## 三、SEI 评估矩阵与适用限制

`evolve.py` 用文件和关键词特征计算 0–100 的结构成熟度参考。具体分值以脚本输出为准，不能由高分推断代码安全、领域正确或实际负向拦截有效。

| 维度 | 满分 | CLI / HYBRID / MCP / PIPELINE | PROMPT |
|---|---|---|---|
| Architecture | 20 | SKILL.md、references、scripts、tests | SKILL.md、references、evals |
| Tooling | 20 | 依赖与机读输出特征 | 输出结构、示例、反幻觉边界 |
| FactCard | 20 | 分层事实卡与基线特征 | 同左 |
| Safety | 20 | 只读与显式授权声明 | 无破坏与确认边界声明 |
| Verification | 20 | 自测、负向与 AST 特征 | 评测集、反例与对抗性输入 |

85–100 为成熟度参考区间，60–84 为进阶区间，低于 60 提示结构可能缺项。该等级不是发布硬门，不为跨过分数线添加无用脚本、空测试或重复措辞。

## 四、完整报告与分层事实卡

### 完整报告

用户要全面体检或需要归档时使用 `--report` / `--report-file`，包含档案、摘要、分类检查明细、修复处方与后续选项。默认会话只给关键发现，保留路径和复现证据，不展开每个通过项。

### 标准分层事实卡

| 层级 | 实测内容 | 判定依据 |
|---|---|---|
| L1 静态 | 实际静态 OK / WARN / FAIL | 静态结论与动态结果分开 |
| L2 动态 | NOT_RUN / SKIPPED / PASS / FAIL | 来自真实执行结果，不以传了参数代表成功 |
| L3 SEI | 实际分数或未评估 | 仅作结构参考，不单独决定交付 |

- `NOT_RUN`：没有请求动态执行。
- `SKIPPED`：请求动态执行，但没有可自动运行的 selftest；tests/evals/Makefile 需另行执行并记录。
- `PASS`：selftest 退出码为 0 且明确的 PASS 结论一致；不代表所有业务路径或负向用例都正确。
- `FAIL`：selftest 失败、退出码与结论矛盾、超时或无法启动。

阶段导航只列实际完成与剩余步骤；若任务已完成就交付，不要求用户再回复“继续”才能完成原请求。
