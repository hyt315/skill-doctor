## 一、四件套详解

### 1. 静态口径对齐
对齐三方：SKILL.md 承诺的 ↔ scripts 实现的 ↔ references 描述的。

操作：audit.py 跑出结构/引用/静默失效/安全四类结果后，人工补两类脚本抓不到的：
- **阈值口径**：数字类规则全树搜索（上限 N 个、字数 ≥X），多处出现逐条比对
- **流程闭环**：SKILL.md 画的流程图每个箭头都有实现，每阶段产物都有消费者

### 2. 动态实跑
把被审技能自己声称的验证真跑一遍。

操作要点：
- 跑前记录环境（Python 版本、OS、关键依赖版本）——环境性缺陷的复现依赖
- 优先跑 selftest；没有 selftest 本身就是重要发现（记 FAIL：技能不可回归）
- 跑前确认命令作用域（临时目录/只读），避免污染被审技能目录
- 结论只认：退出码 + 末行 RESULT + 产物文件三者一致
- **selftest 输出约定（写给被审技能作者）**：成功收尾打印 `SELFTEST PASS (N checks)`，失败打印 `SELFTEST FAIL` 并以 rc=1 退出。audit.py 的 DY003 只按这些字面量判定结论——打印中文结论（如"全部通过"）且 rc=0 会被误判为实跑失败（坑 30）

### 3. 负向用例
每道被审技能声称的"硬门"，构造该 FAIL 的输入验证它真拦。

构造模式（按门类型选）：
| 门类型 | 破坏夹具 |
| --- | --- |
| 文件齐全门 | 抽掉一个必需产物，重跑门 |
| 内容质量门 | 构造超限样本（超长段落/超量元素） |
| 一致性门 | 只改三处中的一处（另两处留旧值） |
| 新鲜度门 | touch 上游文件不重跑下游 |
| 回读门 | 提交后篡改一处内容看能否发现 |

验证标准：门必须 FAIL 且 rc≠0。放行了 = 静默失效，最高优先级 FAIL。

### 4. 坑库对照
`坑库.md` 逐条过"检查方法"列。标"自动"的看 audit.py 输出即可，标"人工"的现场判断。发现新坑当场回写坑库。

## 二、触发用例四分类（借力 OpenAI eval）

评估技能触发可靠性时（是否该激活/是否误激活），构造四类 prompt：

| 类型 | 目的 | 构造 |
| --- | --- | --- |
| 显式 | 点名技能也能触发 | 直接写技能名 |
| 隐式 | 不点名但场景完全匹配 | 只描述任务场景 |
| 情境 | 带噪声的真实请求 | 场景+无关上下文 |
| 负向 | 相邻请求不得触发 | 只改既有产物的请求（易误触发点） |

前两类该触发、末类不该触发。10-20 个用例即可覆盖单技能。注：触发测试需要宿主 Agent 环境手工跑，audit.py 不自动化此项，作为方法论保留。

### 触发率量化（agentskills.io 描述优化法）

| 指标 | 目标值 | 做法 |
| --- | --- | --- |
| 正例触发率 | >0.5 | 8-10 条该触发的 query，每条跑 3 次取均值 |
| 负例触发率 | <0.5 | 8-10 条不该触发的 query（必须含 near-miss：共享关键词但任务不同） |
| 泛化验证 | 通过 | 用 5-10 条**全新** query 复测，不拿训练过的 query 自证 |

拆分防过拟合：train 60% / validation 40%，只用 train 失败指导改描述，约 5 轮迭代足够。负例触发率不达标说明 description 过宽，需加排除词或边界。

## 三、成功四目标检查（OpenAI Evals 扩展）

静态检查覆盖的是"文档自洽"，端到端评估回答"技能真的好用吗"。审查时按四目标各设 must-pass 检查：

| 目标 | 问什么 | 检查示例 |
| --- | --- | --- |
| Outcome 结果 | 任务完成了吗 | 产物存在、应用可运行、关键文件已生成 |
| Process 过程 | 步骤走对了吗 | skill 被调用、工具顺序符合预期、无跳步 |
| Style 风格 | 输出符合约定吗 | 命名/结构/格式符合 SKILL.md 承诺 |
| Efficiency 效率 | 有没有浪费 | 命令循环检测、token 用量在合理范围 |

做法：小提示词集（10-20 条，含四分类触发用例）跑真实会话，确定性检查（文件/事件存在）+ Rubric 评分（结构化为 JSON 的 0-100 分）混合。每次修复都转化为回归用例，不设固定通过率，用可比较分数随时间追踪。

## 四、审查报告格式

写入被审技能目录 `audit-report.txt`：

```
技能审查报告：<技能名> <日期>
环境：Python x.x / <OS> / 依赖版本

检查结果：
OK   [类别/规则码] 检查项
WARN [类别/规则码] 检查项（证据）
FAIL [类别/规则码] 检查项（证据：文件:行号 / 命令输出）

共 N 项，通过 x，WARN y，FAIL z

问题清单：
  1. [规则码] <问题>
     修复：<最小修复路径>
     验证：<修复后如何确认>

修复策略：<单项按最短路 / 多项取最深根因 XXX，从根因修起>
RESULT PASS|FAIL
```

## 五、分级修复决策

| 场景 | 策略 |
| --- | --- |
| 单项问题 | 按该项最小修复路径，修完只重跑受影响检查 |
| 多项并存 | 找最深根因——表面多个症状常同源（如"文档脚本口径打架+报告过期"可能都是"无一致性 lint"这一个根因），从根因修 |
| 负向用例发现的新失效 | 修复 + 坑库回写 + 同类门全查一遍 |
| 修复动到流程结构 | 回到被审技能自己的回滚表（若有）按阶段重跑 |

红线：审查者不代修；每条 FAIL 带证据；不确定降 WARN 并写验证方法。

## 六、大改安全验证流程（治疗流程，2026-08-23 源自 md2wechat 减法改造实战）

诊断之外，医生还要会安全地做手术。对技能做结构性大改（重构 SKILL.md、拆分阶段卡、迁移规则）时按此流程，防止「治好了 A 弄坏了 B」：

1. **沙箱先行**：完整复制技能到独立目录（排除 `.git`、`projects/`、`.private/` 等隐私与产物目录；脚本自校验需要假凭据时，填格式正确的一次性假值），一切改动只在沙箱做，正式目录冻结；
2. **基线回归**：改动前在沙箱跑一遍技能自己的全部回归（selftest/lint/哈希校验），记下基线——改后出红才能确定是改动引入，不是复制缺损；
3. **内容锚点对账**：结构性搬迁（拆文件、合并、删减）前后，用功能锚点词清单（命令名、参数、关键阈值、枚举值、文件名）grep 新旧组合逐一核对，防「搬家丢内容」；清单指针化搬迁时尤其要查目标位缺条目（坑 32）；
4. **三重回归 + 差分对比**：改后重跑全部回归须与基线同绿；阈值类改动同步改一致性 lint 断言，对账总数只增不减；
5. **全链演练**：跑一篇最小真实任务走完全流程（占位素材可，校验门必须真过），第一次执行卡壳的位置就是文档暗环节（坑 33），当场补文档；
6. **逐字节确认后合并**：合并前 cmp 逐文件比对沙箱与即将上线的版本；正式目录先 git 提交还原点，再拷贝、重跑回归、skill-doctor 终审，全绿才算治疗完成；
7. **病例归档**：改造中发现的新病型按坑库格式回写（现象/根因/修复/预防/检查），改过的坑标注实战验证来源——医生的医术就是这么攒出来的。
